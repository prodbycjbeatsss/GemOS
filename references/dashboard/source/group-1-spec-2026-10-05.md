# GemOs dashboard cards — specification sheet

**Working draft · 5 October 2026**  
**Scope:** shared rules for dashboard cards, with Section 1 (1.1 and 1.2) as the first worked example. This is a review document, not a locked template for the remaining cards. Values marked **proposed** should be checked on an Android phone before adoption.

## Decisions already made

- Cards in the same dashboard group use the same height at a given screen width. A change from zero data to many items must not move the cards below it.
- Groups can use different heights. A leaderboard, dense checklist, and compact number card do not need the same internal arrangement.
- Show only the amount of data that fits. An explicit action opens the rest in a separate view or overlay. No hover-only content on phone.
- Each card has one footer. A supporting action can sit left; the full-view link sits right. Do not add a second action strip. In 1.1 the right action is **Release management →**; in 1.2 it is **Release details →**.
- 1.1 displays at most three upcoming projects, with project names, dates and Next Up / Scheduled / In Progress. A project counts as Scheduled when its one main video and six shorts are scheduled. **Next Up** (the first ready project) and **Scheduled** use a restrained green badge; **In Progress** stays neutral. An unfinished first row must say In Progress, not green Next Up. When there are more than three projects, **Show all** opens a dialog. The third preview project is Potter Payper - Air Max 90s, shown as Scheduled; the three consecutive scheduled projects make the preview **3 Weeks Ahead**. Preview-only 3/1/0 week controls are not shown on the dashboard card.
- 1.2 has seven required parts. Its seven ticks and Pass labels show readiness, not publication or scheduling. The asset rows are informational. The bottom-right **Release details →** opens the explanation. **Sync** sits on the footer’s left, without a circular background. The 1.2 Test control is gone.
- 1.2 Shorts means six source files, one for each Tuesday through Sunday; a source file may be posted to several platforms. A missing main video and missing stems can both be represented at once.
- A sync request should rescan Google Drive once a real connection exists. The present standalone preview cannot connect; it says **Not synced** and then **Drive not connected** when pressed.

## Dashboard geometry

| Item | Current Section 1 preview | Proposed rule for later groups |
|---|---:|---|
| Card group width | Full available width up to 960 CSS px; centred when the page is wider | Cap each group based on its card type rather than stretching it across a desktop. |
| Card width / columns | One column below 840 CSS px; two equal columns from 840 px. At the 960 px cap, each card is 470 px wide with a 20 px gap. | Switch only when both cards remain readable. Keep a single column on normal mobile widths. |
| Group 1 card height | 512 CSS px at widths ≥360 px; 532 CSS px at 320–359 px | Keep both 1.1 and 1.2 equal. Increased after the Android screenshot showed the Shorts row clipped at 480 px; check the revised height on the phone. |
| Gap between cards | 20 px | 16–20 px, consistent inside a group. |
| Card inset | 20 px below 640 px; 24 px from 640 px | 20/24 px. |
| Card corner | 32 px | Keep the large spotlight corner only for cards using this visual treatment. |
| Recessed panel corner | 22 px | Keep the same corner across comparable panels. |
| Row corner | 12 px | 10–12 px. |
| 1.1 project row | At least 54 px tall, 8 px vertical / 10 px horizontal inset; 6 px between rows | Keep names and dates readable; allow a long name to wrap without changing the card slot. |
| Minimum button target | 44 × 44 px for major actions in this preview | Aim for 44 × 44 CSS px for touch, including icon-only actions. |
| Overlay width | Up to 480 px, constrained to 92vw | On narrow phones, use a scrollable sheet/dialog within the viewport. |

**Sizing process for each next group (proposed):** first decide the maximum dashboard content for that card, then measure the tallest legitimate state at 320, 360, 390 and 412 CSS px, plus the two-column width. Choose one height for every card in that group at each breakpoint. Record the chosen pixel values here only after that group is reviewed. Do not force an unreviewed group into Group 1’s 512 px slot.

**Text enlargement exception:** fixed dashboard height is a normal viewing rule, not permission to cut off content when Android font scaling or browser zoom is increased. At large text settings, retain the primary value and action; allow the page/card to reflow or offer a clearly labelled full view. Avoid a focusable control hidden behind `overflow: hidden`.

Both Group 1 cards begin their icon and heading at the same top inset. They share a 58 × 58 px glyph, 12 px from glyph to label, the same main-title type scale, 4 px to the subtitle, and 16 px from the heading block to the recessed panel. Their footers share the bottom edge. The panels are allowed to have different heights: 1.1 shows up to three projects; 1.2 shows all seven required parts. Empty space is preferable to stretching rows or inventing data.

## Card parts and placement

| Part | Placement and rule | Section 1 example |
|---|---|---|
| Identity | Small label above the main value or project name. | Release Buffer; Pre Release Checklist. |
| Main answer | Most visible text; one answer to “what is the state?” | “3 Weeks Ahead”; “Teeth & Claws” with “7/7 Files Ready” below. |
| Supporting information | Recessed area below the answer, limited to a known number of items. | Up to three projects in 1.1; seven asset parts in 1.2. |
| Status | Put the status next to the information it describes, expressed in words and/or counts as well as colour. Do not add an extra global “ready” badge if the 7/7 and Pass labels already say it. | Project row labels; asset Pass/Missing labels; 1.1 count and background. |
| Footer | One bottom boundary and consistent baseline. Left is for a small supporting action or freshness when needed; right is for the route to the full view. | 1.1 Release management → right; 1.2 Sync + sync state left, Release details → right. |
| Full view | Explicit action near the truncated content, or the footer detail link. | 1.1 Show all within Upcoming Releases opens a dialog. |

**Do not apply one internal template to everything.** A list card reserves rows and a Show all action. A checklist card reserves every required part and a detail explanation. A metric card needs a value, unit, period and comparison. A chart card needs axes/legend, period and a full chart view. We will set the detailed structure and group height when each card is reviewed.

## Type and spacing

| Role | Current Section 1 | Proposed cross-card target |
|---|---|---|
| Body font | Inter | Keep Inter for controls, labels, dates and descriptive copy. |
| Display font | Poppins | Use only for the main figure or name when it improves emphasis; avoid several display weights per card. |
| Main answer | 24 px mobile; 30 px from 640 px, bold | 24–30 px, with enough line height and a two-line plan for long names. |
| Card label | 11 px uppercase, tracked | Increase to at least 12 px when reviewing phone readability. |
| Project name | 14 px | 14–16 px; allow wrapping so names are not silently cut off. |
| Supporting date | 12 px | 12–14 px; test contrast against each state gradient. |
| Tiny badges/detail | 9–11 px currently | Target at least 12 px for readable text on a phone. This is a recommendation, not yet implemented in 1.2. |
| Spacing increments | 4, 6, 8, 12, 16, 20, 24 px appear in the preview | Prefer a compact set: 4 / 8 / 12 / 16 / 20 / 24; use 6 only for tightly paired icon/text. |

Avoid fitting more information by shrinking body type. Shorten supporting copy, move extra detail to the full view, or give that group a taller fixed slot.

## Colour, status and motion

| Meaning | Current Section 1 visual | Required accompanying text |
|---|---|---|
| 1.1 healthy buffer | Blue → deep slate gradient | Weeks Ahead count and scheduled date. |
| 1.1 project ready to post | Subtle green badge `#d1fae5` on translucent emerald; not a whole-card green surface | Next Up or Scheduled, only when the main and six shorts meet the scheduling rule. |
| 1.1 project unfinished | Neutral translucent white badge | In Progress. |
| 1.1 one future week | Amber → dark gradient | “1 Week Ahead”; project dates/status. |
| 1.1 zero future weeks | Rose → deep slate gradient | “0 Weeks Ahead” and honest empty or in-progress content. |
| 1.2 all seven parts present | Blue → deep slate gradient, green checks | “7/7 Files Ready” and Pass labels. |
| 1.2 any required part missing | Rose → deep slate gradient, missing row | Correct count plus Missing on each affected part. |
| Sync freshness | Footer text, separate from release status | Not synced / Drive not connected now; later use last successful sync time and error text. |

**Proposal for shared semantics:** reserve green for a specific completed/pass item, amber for attention, rose for blocked/missing, and blue for the established spotlight surface. Do not require an entire card to turn green to mean “ready.” Background colour can reinforce a change but must never be the only explanation. A glow is decoration, not a status signal. Use the same state words across cards only when they truly mean the same thing; “ready” does not mean “scheduled.”

Current gradient stops are blue `#0284c7 / #0369a1 / #0f172a`, amber `#d97706 / #b45309 / #1c1917`, and rose `#e11d48 / #9f1239 / #0f172a`. They are current preview values, not an assertion that every text combination passes contrast. Avoid continuous pulsing for status. Any decorative transition should obey reduced-motion settings.

## Data and empty states

- Every tracking card should identify its **subject**, **current state**, **time period or relevant date**, **source/freshness** when automated, and **next available action** where one exists. Do not invent a next action merely to fill a slot.
- 1.1 counts consecutive, fully scheduled future calendar weeks using Europe/London dates. The count stops at the first missing or unfinished week. Its “You’re good until…” date comes from the last confirmed scheduled main/short video within that covered stretch (and the current week when scheduled). If later videos exist beyond a gap, show “Schedule has a gap” rather than implying uninterrupted cover. Zero projects uses the simple “No upcoming projects” empty state. Its preview states can still be exercised in JavaScript without visible test controls.
- 1.2 is a file-readiness check. Seven of seven parts must pass. It must not claim a project is scheduled or already published. A newly saved FLP should not be assumed final without a dependable unfinished marker or another confirmation rule; the exact Drive detection rule remains to be decided.
- A failed or stale sync must be shown as such, separately from the last known file status. Proposed later copy: “Updated 10:42” after success; “Sync failed · last checked 09:10” on error. The displayed readiness needs a clear freshness rule before automation is trusted.
- Loading, empty, partial, stale and error states should all fit the same normal card slot. Keep the title and full-view action available. If data exceeds the row budget, state how much is hidden and put it in the full view.

## Interaction and overlay rules

- A row that opens something must look and behave like a button/link. A read-only asset row must not suggest it can be tapped. Put the detailed explanation behind the visible **Release details →** link.
- Use **Show all** only when items are hidden. It opens a labelled modal list and preserves dashboard height. The modal can scroll; Escape/backdrop dismissal and focus return should work. On Android, test Back as well as the on-screen close control.
- Sync should have a visible result, not just spin. When connected, show progress, success time or a precise error. Prevent repeat requests while a sync is running; keep the previous known result visible with its age.
- The preview Sync action is intentionally a placeholder. Do not present its press as a completed Google Drive scan.
- Do not hide necessary information in hover effects. Tooltips may clarify an icon on desktop but need a touch equivalent.

## Accessibility acceptance checks

1. Test 320, 360, 390, 412, 768, 1024 and 1280 CSS px, portrait and landscape where relevant. No clipped title, count, badge, footer action or focus ring. Verify the two Group 1 cards remain equal height in zero, normal and overfull states.
2. Check text against every actual gradient position and semi-transparent panel, including amber and rose states: WCAG AA normal text **4.5:1**, large text **3:1**. Check meaningful component boundaries and focus indicators at **3:1**. The current preview has not been fully measured.
3. Aim for 44 × 44 CSS px touch targets. WCAG 2.2 AA has a smaller minimum with exceptions, but 44 px is a practical Android target. The current 1.2 nine-pixel badges and some toolbar controls need review; badges are informational, not targets.
4. Test Android font scaling and 200% browser zoom: preserve core content and actions. At these settings a fixed pixel slot may need a reflow exception.
5. Use programmatic names for actions; expose state changes in text. Check modal focus entry, Escape/Back, return focus, and keyboard order. Honour reduced-motion settings.
6. Verify dates use the intended timezone, long artist/track names wrap, and the six-shorts explanation remains available even when the dashboard row is compact.

References: [WCAG 2.2 contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), [target size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).
